## 事故：清理 TEMP 导致用户运行中的旧版失效

**现象**：用户点「开始」后 `output_stl/output_stl1028/` 目录被创建（10:20）但里面始终没有 STL。

**根因（我的操作导致）**：旧版 exe 是 onefile，运行时把 OpenSCAD（43MB）解包到 `%TEMP%\_MEI*\OpenSCAD\openscad.exe`，界面里的 OpenSCAD 路径就指向那里。我在 10:26 清理测试残留时，把用户**正在运行**的那个 _MEI 目录一起删了 → 之后每次调 OpenSCAD 都失败，所以只建目录不出文件。

**教训**：
- 不要清理 `%TEMP%\_MEI*`，除非先确认没有对应程序在运行（`tasklist` 查进程）。
- PyInstaller onefile 程序的临时解包目录是运行期依赖，不是垃圾。
- 以后清理临时目录前先 `tasklist /FI "IMAGENAME eq <exe>"`。

**修复**：关掉程序重新启动即可（重新解包）。已实测：启动旧版 → 取它的 `_MEI*/OpenSCAD/openscad.exe` → 跑 batch 2 个名字 → 成功生成 AVA.stl(60KB)、BELLA.stl(192KB)，链路恢复正常。

**给用户的判断方法**：点开始后日志框应出现
`[时间] 开始任务` → `[时间] OpenSCAD 版本： OpenSCAD version 2021.01` → `[时间] [生成] (1/N) 名字: XXX …`
第一个名字要等 5~30 秒（OpenSCAD 冷启动），期间日志不动是正常的；若卡在「OpenSCAD 版本」那行或出现「任务失败」，才是环境问题。

## 旧版重新打包（v1.3.0）：1~2 分钟/个 → 0.8 秒/个

用户要求「重新打包可用的高效的版本」。已完成，产物 `dist/legacy/PJ1Program/`（+ zip 35MB）。

### 根因排查（三个，按影响排序）

1. **`stamp_template.scad` 文字底面与底座顶面完全共面**（z 都等于 `base_height/2`）。
   CGAL 做 union 要反复切分共面面片：TESS 单个 13.6s，纯 text 只要 0.84s，纯 cube 0.7s。
   加 `overlap = 0.05`（文字下沉 0.05mm、挤出高度 +0.05）后 **13.6s → 3.4s**，
   外形尺寸完全不变（36.0 × 6.168 × 16.0 实测对比），面片数略增。
   **这是本次最大的单点收益，且与打包方式无关** —— `.py` 方式也一起变快了。
2. **旧 exe 用 `--onefile` 且把整个 `OpenSCAD\` 打进包里**：每次启动解压到新的
   `%TEMP%\_MEIxxxxx\`，OpenSCAD 路径每次变；配置也写进 `_MEIPASS` 所以「参数记不住」。
3. **`--windowed` 下 `subprocess` 没做重定向**：OpenSCAD 输出没地方去，
   出错时完全静默（用户看到的就是「点了没反应」）。

补充：曾怀疑「fontconfig 缓存与路径强绑定」，实测**不成立** —— 把 OpenSCAD 整份
复制到 `/tmp/osc_test` 全新路径跑，仍是 7.1s（与固定路径一致），因为缓存落在
`%LOCALAPPDATA%\fontconfig\cache`，按字体目录做 key，系统字体不受影响。

### 改动

- `program/batch_3Dnames.py`
  - `_app_dir()`：frozen 时返回 exe 目录（不是 `_MEIPASS`）；`_resource_dir()` 返回 `_MEIPASS`
  - `script_dir()` → `_app_dir()`，配置写在 exe 旁边；`_abs_in_script_dir()` 先找 exe 同级再找资源目录
  - `_detect_openscad()`：exe 同级 `OpenSCAD\` → 项目便携版 → 系统安装版
  - `_heal_config()`：配置里路径失效自动重探测（换电脑/挪目录不用手改）
  - `batch_generate_stl(..., workers=0)`：`ThreadPoolExecutor` 并发，0=按核数封顶 4
  - `_no_window_kwargs()`：`CREATE_NO_WINDOW`，windowed 下不再闪黑框
  - 子进程 `capture_output + encoding="utf-8", errors="replace"`，失败时把报错写进日志
  - 去重（并发写同名文件会写坏）、`_safe_filename()`、进度 `[完成] (n/total) x KB y s`
  - `_ensure_streams()`：windowed 下 `sys.stdout is None`，print 会 AttributeError
  - `_write_crash_log()`：崩了写 `PJ1Program_crash.log`
  - GUI 新增「同时生成（并发数）」一行；日志框字体改用 `Microsoft YaHei UI`
    （Tk 默认字体无汉字 → Windows 回退中文字体但行高仍按原度量算 → 相邻行重叠）
  - `DEFAULT_NAMES_TXT = ""`（原来填个不存在的 `names1230.txt`，容易误导）
- `program/stamp_template.scad`：加 `overlap = 0.05`
- `tools/build_legacy.py`（新增）：`--onedir`，OpenSCAD 不打进 exe 而是放 exe 旁边
- `tools/gui_smoke.py`：`PrintWindow` 抓图（不受遮挡影响）+ 64 位句柄 argtypes +
  `--settle` + 尺寸兜底重试。**ImageGrab 抓的是屏幕像素，窗口被压住就拍到别人**

- **PyInstaller 覆盖已有 `dist/<name>` 会先 rmtree**，上千文件触发

即：**字恒定 → 间距微调 → 粗细微调 → 算出成品多宽**。
旧版 `batch_3Dnames.py` 就是按这个思路做的，但底座长度是按
「字符数 × 6 + 6」查表估的（2→18、3→24、5→36、13→65），
假设每个字母都占一个字号宽。实际字母平均只占 3.1~3.5mm，
所以旧版底座对短名字严重过宽（TESS 给 30mm，文字只占 12.7mm）。

用户原本的困惑："旧的程序不用调整宽度，可以根据字符数自适应宽度"。
真相是旧版把宽度当**结果**，新版原来把宽度当**输入**，两者方向相反。

### 实现

`StampSpec.width_mode`：`"auto"`（默认）| `"fixed"`

| | auto（新，默认） | fixed（原有） |
|---|---|---|
| 输入 | auto_size_mm + auto_spacing | target_width_mm |
| 求解 | 每个名字的 base_len | 每个名字的 size + spacing |
| 函数 | `metrics.fit_auto()` | `metrics.fit()` |

- `FitResult.base_len_mm`：auto 下逐名不同，fixed 下恒等于 target_width
- `StampSpec.base_len_for(w)` 与 `available_mm()` 严格互逆（有测试守着）
- 模板渲染统一走 `fit.base_len_mm`，两种模式共用一条路径

### 关键决策：auto 模式不套用 edge_mm

第一版实现让 auto 也用 `size_bounds()`，结果 6mm 字号被压到 5.71mm。
根因是 `edge_mm=0.2` 的舒适余量：`(6-0.4)/(0.7349*4/3)=5.72`。
但旧版一直是 6mm 字配 6mm 底座（字高 5.88mm，贴边但能打印）。

**结论**：fixed 模式的字号是算出来的，留余量合理；auto 模式的字号是用户
指定的，只认"字高不得超过底座宽"这条硬约束。超出才压，并提示
"想把底座宽度加到 X"。

另外实测发现 **不同字体字高比差异很大**：Daziji_V1 是 0.7349
（6mm 字号字高 5.88mm），Daziji_V5 是 0.803（字高 6.43mm，6mm 底座装不下）。
所以测试里不能写死 `base_width_mm=6.0`，要按 `cap_height_mm(6.0)` 算。

### 并发

`AppConfig.workers`，0=自动（min(4, cpu_count)）。
`ThreadPoolExecutor` + `as_completed`，要点：
- 结果按 index 收集，最后 `sorted(results)` 落盘，保持清单原顺序
- 日志加锁（`say()`），否则两条日志会互相插进对方中间
- cancel 要在三处检查：调度前、process 开头、as_completed 里
  （只检查调度前不够——并发时任务在取消信号后才被调度到，
   `test_batch_respects_cancel` 就是这么挂的）

## v2.2.0：单模式（限宽）+ 界面重做（已完成并打包）

用户最终确认的规则：**只有一种模式** —— 字号你给，底座长度按名字算，
但不超过「最长不超过」；短名字不补齐；超宽先压间距（1.00→0.85）再缩字号，
缩到 2.5mm 仍超判「超长」。压缩必须在界面上标出来。

关键实现决策（偏离原设计文档，已写进 `docs/plans/2026-10-28-single-mode-redesign.md` 第九节）：
- 删掉 `edge_mm`（限宽只用「字高 ≤ 底座宽」硬约束，留余量会变成死字段）
- 加 `GEOMETRY_TOLERANCE_MM = 0.05`：加粗 0.08mm 只让字高超 0.04mm，
  严格比较会把 6.00 压到 5.96 并在每行标「限字高」，是噪音
- 探针偏差比回灌 `fit(width_scale=)` 重新求解，否则 1.5% 偏差在 60mm 上限上是 0.9mm
- 结果表加尾部占位列，否则名字列 stretch 会把多余宽度全吃掉
- 状态标签 5 个：正常/已压缩/已缩字/限字高/超长

踩过的坑：
- `tk.Text` 默认 `height=24`，行号列不显式给 `height=1` 会把整个名字清单区撑到 400px
- Pillow 预览 4px/mm 太小看不清，改 8px/mm + 最大高度 74px
- 文案 bug：加粗超限时只写「字高 5.88 超过 6.00」自相矛盾，必须把 2×加粗算进去

测试 103 项（93 单测 + 10 端到端）全绿；`verify_build.py` 8 项全通过；
`gui_smoke.py` 截图正常。exe 22.0MB（Pillow +7MB），zip 64.4MB。
commit `7669ca8`。
